# PostgreSQL Schema Initialization — Lessons Learned

## Context

This document captures what we learned deploying CloudNativePG (CNPG) and the
`streamsage-schema-init` Job via ArgoCD for the first time in the dev POC environment.
It is intended to inform the approach for staging, QA, and production.

---

## What CNPG Owns vs. What You Supply

Understanding this boundary is the most important thing to get right before deploying
to any environment.

### Secrets CNPG auto-generates (do NOT pre-create these)

| Secret name | Contents | When created |
|---|---|---|
| `<cluster-name>-superuser` | `username`, `password`, `pgpass`, `uri` | Immediately on cluster creation |
| `<cluster-name>-app` | `username`, `password`, `pgpass`, `uri` | Only if `bootstrap.initdb` has both `database` and `owner` AND a matching `managed.roles` entry |
| `<cluster-name>-ca` | CA certificate | On cluster creation |
| `<cluster-name>-server` | TLS server cert | On cluster creation |
| `<cluster-name>-replication` | Replication cert | On cluster creation |

**If you pre-create any of these with the same name, one of two things happens:**
- CNPG adopts your version and uses whatever password you put in it — even if it's wrong or
  was previously set to something else in the database. This causes auth failures.
- ArgoCD later prunes the secret (if `prune: true`) and CNPG can't recreate it fast enough,
  causing `CreateContainerConfigError` in any pod that mounts it.

### Secrets YOU must supply (CNPG reads these as inputs)

| Secret name (convention) | Purpose | Keys required |
|---|---|---|
| `<cluster-name>-app-credentials` | Sets password for managed app role via `spec.managed.roles` | `username`, `password` |

Use a name that **cannot collide** with CNPG's auto-generated names. The `-credentials`
suffix convention is safe.

## What Went Wrong in Dev

### 1. Superuser secret naming collision
We pre-created `streamsage-db-superuser` (matching CNPG's auto-generated name) with
`prevault-superuser-dev` as the password. CNPG bootstrapped with no password on the
postgres user (because `bootstrap.initdb.secret` was later removed), leaving the
superuser with a null password. External TCP connections require a password, so all
connections failed with `password authentication failed`.

**Resolution:** Set the password directly via `ALTER USER postgres PASSWORD 'prevault-superuser-dev'`
from inside the pod (unix socket, no password required), then kept the secret in git
to match. ArgoCD manages the secret; CNPG reads it as the source of truth.

### 2. ArgoCD prune fighting CNPG secret ownership
When we removed `streamsage-db-superuser` from git, ArgoCD's `prune: true` deleted it
from the cluster. CNPG tried to recreate it but ArgoCD deleted it again on the next
reconcile. This left the schema-init Job in `CreateContainerConfigError` indefinitely.

**Resolution:** The secret must be present in git so ArgoCD manages it and stops pruning it.
The password in git must match what was set in the database.

### 3. Schema-init Job fired before CNPG finished bootstrap
The Job is at `sync-wave: "10"` and the Cluster is at `sync-wave: "5"`. However
ArgoCD considers the Cluster healthy as soon as the CR is accepted — before CNPG
finishes running `initdb` and generating its secrets. The Job started, couldn't find
`streamsage-db-superuser`, and went into `CreateContainerConfigError`.

**Resolution:** The wave ordering is correct in principle but CNPG's secret generation
lags behind CR acceptance. The Job's `backoffLimit: 3` and `restartPolicy: OnFailure`
handle this — it retries until the secret exists. In practice the Job may fail a few
times before succeeding on a fresh install. This is acceptable but noisy.

### 4. PGHOST DNS suffix
Initial Job spec used `streamsage-db-rw.postgres-dev.svc` as the hostname. This is an
incomplete DNS name — it requires the cluster domain suffix
(`streamsage-db-rw.postgres-dev.svc.cluster.local`) or just the short name
(`streamsage-db-rw`) when the Job runs in the same namespace.

**Resolution:** Changed PGHOST to the short service name `streamsage-db-rw`. When the
Job and the Cluster are in the same namespace this always resolves correctly.

### 5. `managed.roles` does not generate a connection URI secret
We assumed `spec.managed.roles[].passwordSecret` would cause CNPG to generate a
`<cluster-name>-app` secret with a `uri` key. It does not. `managed.roles` only manages
the role password — it does not create a connection secret. The `<cluster-name>-app`
connection secret is generated by CNPG only under specific bootstrap conditions.

**Resolution:** The schema-init Job uses `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`,
and `PGPASSWORD` env vars sourced from `streamsage-db-superuser` rather than a `uri`
key. `psql` picks up all standard `PG*` env vars automatically.

## What Needs to Change for Higher Environments

### 1. Replace plain-text secrets with SealedSecrets

`deploy/apps/overlays/dev/postgres/postgres-secrets.yaml` contains passwords in plain
text. This is acceptable for a dev POC but must not be promoted.

**Action:** Before deploying to staging/QA/prod, encrypt the secrets using `kubeseal`:

```bash
# Install kubeseal CLI and fetch the cluster cert
kubeseal --fetch-cert > pub-cert.pem

# Seal the superuser secret
kubectl create secret generic streamsage-db-superuser \
  --dry-run=client \
  --from-literal=username=postgres \
  --from-literal=password=<REAL_PASSWORD> \
  -o yaml | kubeseal --cert pub-cert.pem -o yaml \
  > deploy/apps/overlays/staging/postgres/postgres-superuser-sealed.yaml
```

Each environment gets its own SealedSecret with its own password. The sealed YAML is
safe to commit to git. The Sealed Secrets operator on each cluster decrypts it.

### 2. Use a stronger, randomly generated superuser password

The dev password `prevault-superuser-dev` is a placeholder. For staging and above,
generate a proper random password:

```bash
openssl rand -base64 32
```

### 3. Review `monitoring.enablePodMonitor: true`

The base `pgcluster.yaml` has `monitoring.enablePodMonitor: true`. This requires the
Prometheus Operator `PodMonitor` CRD to exist. In dev this currently causes a warning.
Ensure the monitoring stack is deployed before postgres in staging/prod, or add a
separate sync-wave ordering for the monitoring stack.

### 4. Consider increasing `backoffLimit` on the schema-init Job

In dev the Job retried 3 times before the superuser secret stabilised. For environments
with slower storage provisioning or more instances to bootstrap, increase to `backoffLimit: 6`.

### 5. Production should use `instances: 3` not `instances: 2`

The dev overlay patches down to 2 instances. Prod overlay should use 3 (matching the
base) for proper HA with a primary + 2 standbys.

### 6. WAL archiving

The CNPG cluster currently has no backup/WAL archiving configured. Before running in
any environment with real data, configure `spec.backup` with an S3-compatible object
store (IBM Cloud Object Storage for this stack):

```yaml
spec:
  backup:
    barmanObjectStore:
      destinationPath: "s3://<bucket>/postgres-backups"
      endpointURL: "https://s3.<region>.cloud-object-storage.appdomain.cloud"
      s3Credentials:
        accessKeyId:
          name: postgres-backup-credentials
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: postgres-backup-credentials
          key: SECRET_ACCESS_KEY
    retentionPolicy: "30d"
```

## ArgoCD + CNPG Coexistence Rules (Summary)

1. **Never pre-create `<cluster-name>-superuser`** — CNPG owns it. If you need a
   specific superuser password, set it after bootstrap via `ALTER USER`.
2. **Keep `streamsage-db-superuser` in git** so ArgoCD doesn't prune it and starve pods.
   The password in git must match the actual DB password.
3. **App user secrets** use a name with `-credentials` suffix to avoid collision with
   CNPG's generated secrets.
4. **Schema-init Job** uses `PG*` env vars, not a URI key. Short service name for PGHOST.
5. **prune: true + selfHeal: true** means anything not in git gets deleted. Every secret
   a pod needs must be in git (or generated by an operator that ArgoCD knows not to prune).
